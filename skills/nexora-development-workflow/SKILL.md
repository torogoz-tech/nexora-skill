# Nexora development workflow

The remote Nexora MCP governs project work. The development agent runs Git, edits code and executes checks on the developer machine. Nexora does not execute local Git, create local environments or inspect the developer filesystem. The Nexora operational CLI and database credentials belong on the server; do not install them on a developer machine for this workflow.

## Plan requirement changes before creating implementation tasks

For requirement-driven planning, read the exact requirement version and call `nexora_features_list` before proposing work. Reuse existing project features whenever the requirement changes an existing capability. Use `nexora_feature_map_propose` with the catalog revision, requirement/version IDs, impact for each existing or new feature, and proposed tasks bound by zero-based feature index. Proposed tasks may be unassigned and do not require an execution workflow. Approval creates pending pool tasks; assignment reserves responsibility and never starts execution. A proposal creates no implementation tasks or features until an authorized human approves it. Do not attempt to approve a proposal through MCP or an API key, create duplicate features to bypass review, or create the proposed tasks separately while the map is pending. If the requirement or catalog changes, inspect it again and submit a revised proposal. Existing approved tasks continue through the task-work process below.

## Read the assignment

Call `nexora_projects_list` (following `next_cursor` with `after`) to discover currently authorized projects, and `nexora_permissions_get` to inspect current authority. Personal MCP keys inherit the member's live assignments: newly assigned projects become available without reissuing a key, and removed access stops applying. Do not treat a previously cached project list as authorization. Read-only personal keys remain read-only; human-only approval and administration are not delegated.

Discover the MCP schemas and consult `nexora_development_workflow_get` for current server guidance. Read the task with `nexora_task_get`, its lifecycle, acceptance criteria, relevant documents, authorized repositories and code context. Tasks may have no project or responsible member. An assignment alone is a reservation, even when assigned to the current developer. When the developer explicitly chooses to start a pending task, call `nexora_task_take` with its current `expected_revision` and a stable request ID. For implementation work, include the explicit `repository_ids` to modify. Taking self-assigns an unassigned task, verifies membership and pins the task-selected published workflow and initial state; never take a reservation belonging to somebody else. Read the resulting published workflow before preparing governed transitions. Projectless MCP operations require explicit installation-scoped task capabilities; a project-scoped key cannot inherit broader human-session access. Never invent a project to bypass this boundary.

Respect repository instructions. Use actual transition IDs from the published graph; do not invent fixed states. Pending tasks cannot transition into execution without Take. `nexora_task_transition` changes state; `nexora_task_move` changes a project's backlog. For governed tasks, a terminal workflow state completes the current stage only. Inspect `nexora_task_stages_list` and transition runs: a final automatic pipeline may be waiting for approval, checks, deployment or delivery. Global completion requires verified production publication. Historical legacy tasks retain their previous terminal behavior. Reassignment of active work returns it to pending and requires another explicit Take.

Read `nexora_task_relations_get` before starting or completing work. Unfinished blocking prerequisites prevent Take and completing them releases the dependency automatically. A parent may start before its subtasks, but all relevant subtasks must finish their pinned current stage before the parent enters its final state. Previous-stage subtasks retain their completed stage history. Decomposition subtasks do not execute final delivery pipelines. Corrective subtasks retain their parent, use the exact tested repository SHA, deliver back to the parent workflow and require the same correction integrated into develop. Never move the parent merely to repair its corrective subtask. Each subtask retains its own responsibility and explicit Take. Archiving unfinished work does not satisfy a prerequisite or child-completion requirement. Relationship changes require current revisions, compatible project scope (same project or both projectless), and authority over the affected tasks; never remove a requirement merely to bypass its approval or completion.

## Prepare a branch locally

For project-linked code work, perform the following after Take. Taking implementation work prepares provider-verified remote task branches for the selected repositories and returns `repository_branches` with a durable `start_run_id`. If preparation fails after taking the task, retry Take with the exact same parameters; normal transitions remain blocked until preparation succeeds. Local checkout and environment preparation remain the agent responsibility. Do not create an alternate local branch to bypass server-assigned origins. Projectless work has no project repository context; do not fabricate repository links or branch reports.

1. Read `nexora_repository_development_policy_get` for the assigned repositories. Defaults are `base_branch: develop`, `branch_prefix: feature`, revision `0`. Policy editing requires separate authorization. Task operations need task read/write/transition; repository context also needs repository read and knowledge read access.
2. Use a published task-only start transition with the explicit `working_branch_reported` guard. Call `nexora_task_work_prepare` with `project_id`, `task_id`, stable `request_id` and `preparation`: `transition_id`, `parameters` with current `expected_revision` and other required transition parameters, and assigned `repository_ids`. Retain the returned session and server-assigned branch names. Preparation does not change state or run Git.
3. Use the agent's existing local Git tools. Match each local checkout to the assigned repository before modifying it. Inspect current branch/status and preserve uncommitted work. Fetch the registered task branch from the appropriate remote and create a local tracking branch at its verified commit. Decomposition branches start from the parent task branch; corrective work starts from the exact tested revision recorded by Nexora. Never recreate the remote branch from the current develop head. Prefer a separate local worktree when the checkout contains other work. Choose a local path yourself; the server does not supply paths. If the base is missing, fetch fails, the branch already exists outside this session, or repository identity is uncertain, stop implementation and report the blocker. Do not reset, clean, overwrite, or stash unrelated work automatically.
4. Inspect the new branch, commit and base locally. Only after successful Git preparation, call `nexora_task_work_report` with `project_id`, `task_id`, `session_id`, stable `request_id` and `report.branches`: each has `repository_id`, assigned `branch_name`, `base_sha`, `head_sha`. Supply all session repositories exactly once. Do not send local paths, credentials, commands, remote URLs or verification flags. Record only actual observed results, never invent a SHA.
5. The returned session contains `report.provenance: agent_reported`, reporting credential and server timestamp. This records the actor's declaration; it does not independently prove branch creation, ancestry, provider publication or the local environment. This local report remains agent-reported. Provider-backed transition actions independently verify actual branch heads, origin ancestry, PRs, checks and deployments; never represent this report as that proof.
6. Request `nexora_task_transition` separately, using the prepared transition, current expected revision and all facts/approvals required by the actual workflow. Begin implementation only after the task reaches the intended state. A branch report alone never advances the task. Keep working in the locally prepared branch/worktree.

## Reconcile and deliver

Use `nexora_task_work_get` to inspect your session after an uncertain response. Retry the same request IDs and payloads. Reports are immutable; do not replace a recorded SHA with a newer HEAD after editing. If task revision, policy or source authority changed, re-read context and reconcile before preparing a replacement session. Preserve existing local artifacts. The server cannot detect an unreported Git failure or enforce local agent behavior; the skill and traceable reports define that responsibility.

Implement and run checks appropriate to the change. Upload relevant screenshots, measurements, patches and actual test results using `nexora_evidence_upload`. Pass evidence IDs to `nexora_evaluate_repository` when evaluation is needed. Distinguish the indexed snapshot, unpublished local edits, supplied evidence and independent verification. Evaluation does not execute tests or prove deployment on the agent's behalf.

Apply later state changes with `nexora_task_transition`; never invent approval or force completion after a conflict. Report task/session, repositories/branches, checks, evidence and blockers. Distinguish local work, pushed commits, merge and deployment. Branch preparation does not authorize push, merge, deployment or workflow/policy edits.

## Governed task purpose and work records

Read the task type purpose independently of its editable display name: `general` work has no workflow, `product_design` requires a primary requirement before Take, and implementation work may link a primary feature. A task has at most one primary requirement or feature. Keep supplemental evidence distinct from the primary planning relationship. Choose the entry workflow on the task before Take. After handoff, an eligible member explicitly takes the task's already pinned destination workflow; do not replace it with another assignment version.

Multiple tasks may be active. Record actual work using `nexora_task_work_log_add`, date and minutes; use the corresponding change/remove tools with current revision to correct your own records. Workflow elapsed time is process history, not hours worked. Only link overtime that was actually approved and covers the recorded work. General work completes through `nexora_task_complete_general`; workflow work never uses this shortcut.

Transition steps run in configured order and use durable checkpoints. Reuse the same request ID and exact parameters after uncertain outcomes. Human approvals authorize pinned parameters and are never fabricated by the agent. A successful code review, merge or pipeline does not itself prove production publication. Release preparation and task inclusion do not complete tasks; publication requires provider-confirmed merged main revision and successful production deployment for every included repository.

Private contributor ratings are an explicit transition action after a technical Code Review. They use verified commit authors and current organization aliases, never the pusher or task assignee as a substitute for authorship. Technical PR descriptions contain the technical review only, never personal ratings. Polling and retrying a completed step must reuse its persisted result. Interrupted AI requests require reconciliation rather than repeated token consumption.
